## Что показала повторная диагностика

Воспроизведение: `.development/review_v04.py`. Скрипт читает код именно из тега
`v0.4.0`, использует существующие кеши и модели, не обучает модели и не меняет ответ.
Результаты: `artifacts/review-v04/diagnostics.json`, `positive_ranks.csv`.

1. **Основные локальные потери происходят при сокращении кандидатов до 50.**
   В проверке на 800 контекстах по полным меткам 55 пропущенных положительных
   объявлений: 8 вне пула, 19 на позициях 51–100, 22 на 101–300, 6 ниже 300.
   Таким образом, 41 из 55 пропусков уже доступны в первых 300 результатах.
   Recall@50 = 0.9321875; @200 = 0.9775; @300 = 0.9825; @500 = 0.98875.
   Полнота всего пула около 0.99. Это локальная оценка; полнота пула на скрытом
   бенчмарке неизвестна. Высокая полнота не исключает пользу дообучения энкодера:
   он может улучшить порядок кандидатов внутри пула.

2. **Прямое обучение использует небольшую часть доступной разметки.**
   Из 467054 уникальных пар лишь 29572 имеют положительное объявление в
   `benchmark_items`: 26556 контекстов, 12174 нормализованных текста.
   Другие пары уже участвуют в статистиках истории, но не обучают текстовый энкодер.
   Всего в train 344825 уникальных объявлений. Их тексты можно использовать для
   обучения, даже если эти объявления нельзя выдавать в финальном ответе.

3. **Режим истории при обучении не полностью соответствует применению.**
   В обучающих OOF-фолдах удаляются все появления текста запроса из истории.
   В бенчмарке 37.36% текстов встречались в train, хотя полностью совпадающих
   контекстов только 4.40%. Локальный срез, названный seen, после удаления истории
   содержит только 71.85% действительно известных текстов. Нельзя считать весь
   этот срез известными запросами при выборе смеси моделей.

4. **Географические несовпадения требуют отдельного анализа.**
   Попадание положительной пары в top-50: 96.21% при одинаковом location_id
   (660 пар), 81.48% при разных (162 пары). Это доли по парам, не макро-Recall
   по запросам. Разные ID не обязательно означают большое расстояние.
   У 427 запросов бенчмарка нет центра локации в корпусе; простое добавление
   центров из train восстанавливает лишь 2. Нужна более содержательная модель гео.

5. **У ранкера разные условия обучения и применения.**
   В среднем 183 кандидата на обучающий контекст против 2193 на локальном инференсе.
   Трудные отрицательные примеры частично выбираются старой HGB-моделью.
   LambdaRank оптимизирует NDCG, а выбираем решение по Recall@50; увеличение
   количества деревьев или одна замена cutoff не гарантируют улучшения.

6. **Найдена небольшая ошибка построения локальных меток.**
   Метки новых 800 контекстов были получены после части удалений из истории.
   В 6 контекстах потерялись 7 положительных объявлений: 815 вместо 822.
   Восстановление полных меток меняет Recall@50 с 0.9325 до 0.9321875.
   Это не объясняет разницу с платформой и не отменяет подтверждённый прирост.
   Полный набор меток надо отделить от изменяемой истории во всех экспериментах.

## Порядок экспериментов

### 1. Исправить протокол сравнения

- Построить неизменяемые gold-метки из полного train до любых purge-операций.
- Явно разделять новый текст, известный текст с новым контекстом, полностью
  известный контекст; отдельно показывать известные и новые положительные items.
- Для неизвестных текстов использовать группировку по нормализованному запросу;
  для известных текстов удерживать контекст и запрещать использование его меток
  в истории. Для полностью известных контекстов без времени/сессий нельзя
  заявлять честную оценку будущих повторных событий.
- Проверять чувствительность к доле новых items: прежние 90% удаления —
  допущение, а доля известных items во всём корпусе не определяет долю известных
  items среди скрытых положительных ответов.
- Зафиксировать основной dev и дополнительный контрольный split. Повторно
  используемые 800 контекстов теперь считать dev, не новым независимым тестом.
- При новых разбиениях проверить исключения для всех обученных компонентов,
  включая замороженные HGB-приоры. При необходимости переобучить сравниваемую
  базовую модель по тому же протоколу.
- Обучающие OOF-признаки строить и для новых текстов, и для известных текстов
  с удержанным контекстом. Выбирать режим по доступности истории при инференсе.

Результат этапа: сравнения вариантов на одинаковых корректных метках, срезах и
источниках истории. Это инфраструктура экспериментов, не ожидаемый прирост сама по себе.

### 2. Усилить текущий отбор: данные, отрицательные примеры, география

- Увеличить число доступных обучающих контекстов в пределах корректных фолдов.
- Использовать текущий сильный ранкер для поиска трудных отрицательных примеров;
  особенно важны кандидаты около границы top-50. Добавить широкий случайный хвост.
- Сравнить группы из 300–1000 кандидатов с текущими 183. Для ограниченного числа
  групп проверить обучение на полном пуле и оценить стоимость в RAM/времени.
- Считать Recall@50 на полном пуле при выборе модели и числа итераций.
- Добавить отдельные географические сигналы: наличие центра, расстояние,
  историческую вероятность перехода, объём истории и её неопределённость.
- Проверить сглаженные переходы search_location → item_location с учётом вида
  услуги. Не вводить жёсткий запрет на другую локацию.
- Добавить объём истории запроса, уверенность и энтропию распределения microcat,
  поддержку точного/похожего запроса. Признаки должны считаться только по
  разрешённой истории конкретного фолда.

Первый кандидат на новую отправку: устойчивое улучшение v4 на этих изменениях.
Каждый блок проверять отдельной абляцией, затем объединять полезные блоки.

### 3. Получить новый обученный сигнал из большей части train

Первый относительно дешёвый эксперимент — предсказывать распределение по
`item_microcat_id` из текста запроса и фильтров. В корпусе 752 microcat.
Использовать все допустимые обучающие пары, учитывать несколько положительных
microcat для одного запроса. Входы для пилота: символьные/словные признаки и
замороженные E5-эмбеддинги. Подать вероятности и неопределённость в ранкер.
Это не использование отложенного `search_category`.

Параллельно по смыслу эксперимента: добавить поиск похожих исторических запросов
по E5 к существующему символьному поиску; проверить кандидатов и статистики из
истории выбранных объявлений. Использовать только train и исключения фолда,
без ручных ответов под query_id.

Следующий GPU-пилот — дообучить query-encoder E5, оставив document-encoder
замороженным. Предвычислить векторы обучающих документов; это позволяет учиться
на парах с объявлениями вне benchmark_items и не пересчитывать весь корпус
после каждого обновления query-encoder.

- Сравнить с исходной E5 на неизменном dev; сохранить исходную E5 как отдельный сигнал.
- Учитывать несколько известных положительных объявлений и дубликаты при выборе
  отрицательных примеров. Отсутствие взаимодействия не является доказанным минусом.
- Обычное накопление градиента не увеличивает множество контрастивных отрицательных
  примеров; при необходимости использовать loss с кешированием представлений.
- Получать OOF-прогнозы обученного компонента для обучения следующей модели.
- Измерять и полноту пула, и итоговый Recall@50: полезность не сводится к полноте.

Полное дообучение двух энкодеров и расширение обучающего поискового корпуса
объявлениями train оставить условными экспериментами: запускать, если пилоты
подтверждают пользу и остаётся время. Расширенный индекс меняет распределение
рангов и требует отдельной проверки. Финальная выдача всегда только из benchmark_items.

### 4. Проверить cross-encoder на top-300–500

Это альтернативный сильный сигнал: совместная обработка текста запроса и
объявления вместо единственного сходства независимо вычисленных векторов.

- Начать с компактной многоязычной модели и небольшого пилота. Измерить реальное
  время, память и вклад в Recall на нашей RTX 5070 Ti 12 ГБ.
- Использовать заголовок, параметры и ограниченное описание. Новую оценку
  передавать ранкеру вместе с географией и качеством объявления.
- Не заменять весь отбор одним текстовым score: цель — наблюдаемый выбор пользователя.
- Сравнить размеры shortlist 300 и 500; контролировать потерю положительных
  объявлений при отсечении. На бенчмарке это 735600–1226000 пар для инференса.
- Дообучение на трудных отрицательных примерах запускать только после пилота,
  с защитой от утечки меток между компонентами.

Если готовый cross-encoder не помогает, не тратить остаток времени на масштабный
перебор. Если помогает сильнее query-encoder-пилота, отдать ему приоритет по GPU.

### 5. Выбрать сочетание, воспроизвести и упаковать

- Смешивать модели при дополнении ошибок; не добавлять модели только ради количества.
- Настройки смеси выбирать по dev, проверять разницу по запросам и проблемным
  срезам. Считать парный bootstrap как оценку неопределённости, не как гарантию
  переноса на платформу.
- Обучить выбранную конфигурацию на всех разрешённых данных, сохранить веса,
  версии библиотек, параметры, seed, точные ревизии открытых моделей.
- Проверить воспроизведение без внешних API, формат CSV и соответствие его SHA256
  конкретной версии кода. Обновить выполненный notebook и описание ошибок/решений.
- Сохранить v4 как резервный ответ. Отправлять содержательно разные локально
  обоснованные улучшения; не подбирать десятки настроек по скрытой метрике.

## Распределение оставшегося времени

Это предельные бюджеты этапов, а не предсказание длительности обучения:

- До 4 часов: исправить протокол и воспроизвести базовую оценку.
- Следующие 7–9 часов: ранкер, трудные отрицательные примеры, признаки истории,
  география, пилот microcat. Получить самостоятельного кандидата на отправку.
- Следующие 12–15 часов: ограниченные GPU-пилоты и развитие лучшего нового сигнала.
- Остаток: выбор смеси и финальное обучение; последние 3 часа зарезервировать
  на воспроизводимость, упаковку, проверку и отправку.

Не ждать завершения всех идей, чтобы сохранить улучшенный ответ. Если этап
съедает бюджет без подтверждённого эффекта, переходить к следующему или к финализации.
