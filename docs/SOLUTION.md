# Генерация кандидатов услуг: итоговое решение

Проверенный на платформе результат: **Recall@50 = 0.914682**. Для каждого
поискового запроса решение возвращает 50 объявлений из фиксированного корпуса.
Отправленный файл — корневой `answer.csv`, его SHA-256:
`8ce7401347beb1806f962ae1e72999fa93c89201b1044cd2433494f50e837d7e`.
Порядок внутри 50 объявлений на Recall@50 не влияет.

## Данные и признаки

Использованы только три предоставленных файла: `train.parquet` с 497 673
наблюдаемыми парами «запрос — выбранное объявление», 2 452 запроса из
`benchmark_queries.parquet` и корпус 189 212 услуг из
`benchmark_items.parquet`. Метки benchmark недоступны; правила под конкретные
`query_id` не используются. Все идентификаторы обрабатываются как строки.

| Источник | Признаки | Зачем они нужны |
| --- | --- | --- |
| Текст запроса и объявления | Нормализованный запрос, заголовок, описание и параметры; BM25, символьный TF-IDF, покрытие токенов | Точные формулировки и опечатки коротких запросов |
| Локальные encoder-векторы | E5 для широкого семантического поиска, дообученный query encoder при замороженном encoder объявлений, BGE-M3 для дополнительного сходства | Синонимы и неполное совпадение слов |
| Структура запроса и объявления | Категория, подкатегория, явные вид и тип услуги, фильтры, цена, рейтинг, отзывы, доступность связи | Отличать похожие по тексту, но разные услуги |
| Локация и история | Совпадение локаций, расстояние, переходы между локациями, частоты взаимодействий, уверенность истории | Учитывать локальность услуги без жёсткого запрета выезда |
| Новые признаки v11 | Совпадение вида/типа услуги, плотность объявлений в локации, дистанционная работа, выезд и взаимодействие выезда с расстоянием | Разрешать пограничные случаи при выборе top-50 |

`search_category` используется как мягкий признак. Если он равен нулю,
категория не ограничивает выбор. Несовпадение фильтра с параметрами объявления
также не удаляет кандидата: в обучающих положительных парах встречались
исключения.

## Алгоритм

1. Лексические и семантические каналы извлекают широкий пул объявлений.
   Локальная полнота пула около 0.995: дальнейший ранкер может выбирать
   только из него.
2. Для пары «запрос — кандидат» считаются текстовые, семантические,
   исторические, категориальные и географические признаки. Векторы корпуса и
   исторические агрегаты заранее сохранены, но не содержат ответов benchmark.
3. Сохранённый LightGBM LambdaRank v10 оценивает 94 признака. Второй
   LightGBM v11 использует те же 94 и ещё 10 структурных признаков. Он
   обучен на 39 672 522 парах из 52 943 групп.
4. Ранги двух моделей объединяются reciprocal rank fusion с весами 50/50.
   Только после этого выбираются первые 50 уникальных `item_id`.

Код поиска и вычисления базовых признаков показан по этапам в
[`solution.ipynb`](../solution.ipynb). Код новых признаков находится в
`.development/rank_features_v11.py`, их обучения — в
`.development/quality_v11.py`, применения — в
`.development/quality_model_v11.py`. Конфигурация весов и SHA-256 артефактов
находится в `config/solution_v11.json`.

## Проверка до отправки

Положительные метки локальной валидации отделены от истории, из которой
строятся признаки. Это исправило раннюю ошибку с потерей семи меток при
очистке истории. Оценки считались по полным пулам для новых текстов и для
известных текстов с новым контекстом. Дополнительно проверялась
чувствительность к доле ранее встречавшихся объявлений.

| Вариант | Локальный matched Recall@50 |
| --- | ---: |
| Повторно оценённый v10 | 0.959901 |
| v11: структурные признаки + RRF 50/50 | **0.961181** |

Относительные признаки BGE и отбор трудных кандидатов обучались и проверялись
отдельно. Они не дали надёжного дополнительного выигрыша относительно
выбранного простого варианта. На ранее использованном контрольном срезе v11
потерял одно попадание из 600 запросов; этот контроль не служил для выбора
весов. После отправки платформа показала рост с **0.911829** у v10 до
**0.914682** у v11. Подробные абляции и ограничения локальной валидации — в
[`EXPERIMENTS_V11.md`](EXPERIMENTS_V11.md).

Перед отправкой CSV проверен независимо: ровно две колонки
`query_id,answer`, все 2 452 запроса без повторов, не более 50 уникальных
объявлений на запрос, каждый `item_id` существует в корпусе и сохраняет
исходный регистр. Архив решения был распакован в отдельную папку; на CPU и
с отключённой сетью notebook создал побайтово тот же CSV.

## Анализ ошибок

- Около 0.5% локальных положительных пар не попадают даже в широкий пул;
  ранкер не может их восстановить. Этот предел показывает направление для
  дальнейшего улучшения каналов поиска.
- Короткие запросы могут обозначать разные виды услуги. Текстовое сходство
  приводило к подмене вида или типа; явные параметры добавлены как мягкие
  признаки.
- Простое расстояние иногда ошибочно понижало выездные и дистанционные
  услуги. Признаки формата работы и их взаимодействие с расстоянием позволяют
  модели учитывать эти случаи.
- Не выбранные пользователем объявления не обязательно нерелевантны.
  Поэтому трудные отрицательные примеры проверены отдельно, но не включены в
  выбранный финальный ранкер без убедительного выигрыша.

## Воспроизведение

Распакуйте `deliverables/solution_v11.zip`, положите рядом с
`solution.ipynb` три исходных Parquet-файла, установите `requirements.txt` и
выполните **Restart Kernel → Run All**. Notebook использует только локальные
веса и проверяет SHA-256 результата. Архив включает нужные модели и код;
исходные данные не дублируются. Для работы с GitHub без большого архива веса
нужно отдельно взять из этого комплекта.

Open-source компоненты: `intfloat/multilingual-e5-small` и `BAAI/bge-m3`
(локальные веса), PyTorch, Transformers, LightGBM, pandas, NumPy, SciPy,
scikit-learn, PyArrow, joblib и SnowballStemmer. Точные версии Python-пакетов
зафиксированы в `requirements.txt`; при применении внешние API не вызываются.
